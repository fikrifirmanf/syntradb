# Initial development baseline

The first run used 100,000 rows, seven measured repetitions, one warmup per route,
and a single client. All result comparisons and the four multi-session snapshot
checks succeeded. [The archived JSON report](results/baseline-2026-10-27.json) contains samples and
plans. Generated JSON files stay local; rerunning the harness replaces `latest.json`.

Both databases used PostgreSQL 18.6 on the same macOS ARM64 machine. Rust used a
release build. PostgreSQL assertions were enabled, JIT and parallel query were
disabled, and `fsync` stayed on. These small warm-cache results are a development
baseline. They do not establish production speedups or mixed-workload performance.

The table shows median server execution time in milliseconds. Planning and client
latency are excluded. The segment path includes full validation of its encoded data.

| Layout | Query | PostgreSQL | Enabled heap | Segment |
|---|---|---:|---:|---:|
| Ordered | All rows | 5.544 | 5.361 | 0.666 |
| Ordered | 10% range | 2.854 | 3.374 | 0.499 |
| Ordered | 0.1% range | 3.079 | 2.593 | 0.480 |
| Shuffled | All rows | 5.569 | 5.395 | 0.693 |
| Shuffled | 10% range | 3.289 | 3.226 | 0.789 |
| Shuffled | 0.1% range | 3.272 | 2.800 | 0.779 |

Ordered range scans pruned 87 and 97 of 98 groups. Neither shuffled range scan
pruned any group. Each segment contained 414,892 encoded bytes, and every scan
validated them all. The lower scan counter therefore does not establish reduced
physical IO. Capture plus destination table creation took 11.843 ms for ordered
data and 13.470 ms for shuffled data.

The visible difference between layouts supports testing physical sort keys in a
later milestone. The native heap numbers also vary across routes at this sample
size; execution times alone cannot establish planner-hook overhead. Follow-up
work needs a production-configured PostgreSQL build, larger datasets, more runs
and concurrent OLTP/OLAP before making product-level performance claims.
